# Growth HQ group-keyword replies

Task GHQ-WA-KEYWORD-001, base `44c2891e5045636751fc6c10bcd9888df62abe73`.

The owner editor is `/crm/channels/whatsapp/keywords`, linked from the existing WhatsApp page. Rules live in existing AppSetting storage and edits use the existing admin session, origin guard and audit log. The portable adapter is `tools/whatsapp-keywords`. Claude's original `normalise` / `findTrigger` implementation is retained in `matcher.cjs`; the original in-memory sending queue is not used.

Each rule selects one business, explicit group IDs, exact or whole-word keywords, a reply and enabled/paused state. `{name}` inserts the requester's first name. Enabling requires the owner to confirm the group invitation promises that private reply. Empty group choices never mean all groups. Overlapping enabled rules for the same group are refused, including across brands.

## Custody and boundaries

The group listener is bound to the number privately configured in `GHQ_WA_LISTENER_NUMBER` (international digits only). The owner scans its QR on a private loopback page inside Codex. A missing configuration or different account is refused before group collection or sending. The QR is held in memory only; credentials and Signal keys use an encrypted atomic snapshot outside the repository. No external browser profile is launched. This uses the unofficial Baileys socket transport; it is separate from MHP's official Meta number, token, webhook and message receipts. It does not grant access to existing phone-created groups through the Cloud API. `GHQ_WA_PAIR_ONLY=true` refuses group/contact reads, message export and sending even after linking; restart without it only after verifying the intended account and the existing rules/outbox.

Only matching group messages, group-name/ID inventory, and private STOP/START controls are submitted. There is no private-chat backfill. Group messages from before a rule was on are read only for a catch-up the owner explicitly requested (see "Catch-up" below): without an open catch-up from Group HQ the listener neither asks the phone for a group's earlier messages nor submits one, and a live group message is still admitted only within five minutes. To be able to ask the phone at all, the listener keeps one sealed file (`catchup/` in its data directory, encrypted and written atomically like the session, mode 0600) holding, per group it is in, the newest stored message only: its WhatsApp message key, time, sender (WhatsApp ID and display name) and that one message's own text. That is the single group message body the listener keeps on disk, it is replaced as soon as a newer message arrives, and it never leaves the computer unless a catch-up finds it matches. Other personal messages are ignored. STOP/START affects only this listener's replies; it does not manufacture MHP/PP marketing consent, SMS consent or a verified canonical CRM contact.

The adapter needs `WHATSAPP_KEYWORD_ADAPTER_SECRET` (32–256 characters), shared only between this adapter and Group HQ, and `GHQ_BASE_URL` (default `https://group-hq.onrender.com`). Use a dedicated secret, not the read-only R72 bridge credential or a Meta token. Session, event-spool and settlement files live under `GHQ_WA_DATA_DIR` or the ignored local `data` folder. Keep that directory private and persistent. It currently runs while the owner's computer is on; a separately hosted always-on listener requires its own reviewed persistent hosting and QR handoff.

## Adapter contract v1

Prefix `/api/whatsapp-keywords/v1`. Each request has `X-GHQ-Timestamp` (Unix seconds within 120 seconds) and `X-GHQ-Signature` (lowercase hex HMAC-SHA256). Signed bytes are `timestamp + "\n" + METHOD + "\n" + pathname + "\n" + rawBody`. No query parameters or redirects. GET body is empty; JSON bodies are UTF-8. Credentials never enter query strings or browser HTML.

- `GET /rules`: `{schemaVersion:1, listenerId:"personal-7510", revision, rules:[{id,brand,name,keywords,message,groupIds,matchMode,enabled}], catchups:[{id,ruleId,since,until,expiresAt,groupIds,pendingGroupIds}]}`. `catchups` (an addition to v1) lists only a catch-up that is open now; `pendingGroupIds` are the groups not yet reported. A listener from before catch-up ignores the extra key and keeps working.
- `POST /groups`: `{listenerId, groups:[{id,name}]}`; group IDs end in `@g.us`. Inventory is capped at 1,000 groups, not selected automatically.
- `POST /events`: `{eventId,listenerId,groupId,senderId,senderPhone,senderName,text,observedAt}`. `senderPhone` is digits only; `senderId` is the actual WhatsApp `@c.us`/`@lid` ID. The adapter obtains the phone mapping from WhatsApp; an unresolved identity is not messaged. Only fresh matching requests are admitted. Exact ID replay is effect-free, changed bytes under the ID conflict (409). Responses identify queued, replayed, already_contacted, ignored or opted_out.
- `POST /catchup-events` (addition to v1): the `/events` fields plus `catchupId`. Admitted only while that catch-up is open and unexpired, its rule is still enabled at the revision it was requested at, the group is one of its groups, the text matches the rule (checked again on the server) and `since <= observedAt <= until` (120 seconds of clock tolerance). After that the same code as `/events` decides: STOP is respected and a person gets a rule's reply once. An event ID already recorded, live or by an earlier catch-up, is `replayed` without effect (no 409 here: the same WhatsApp message read back from the phone need not be byte-identical to its live copy). Outcomes: queued, replayed, already_contacted, opted_out, ignored (wrong group or no match), outside_window, over_cap (the catch-up already queued 300 replies; nothing is queued or recorded) and closed (the catch-up is done, cancelled, expired or unknown). All are HTTP 200 so the listener's outbox always drains. `/events` keeps its 300-second rule.
- `POST /catchups/{id}/progress` (addition to v1): `{listenerId,groupId,status:"scanned"|"unavailable",reachedSince,scanned,matched,unresolved}`. One report per group when the listener has finished reading it: `reachedSince` says it read back past the window's start; `unavailable` says the phone supplied nothing. When every group has reported, the catch-up is `done`. A repeated report or one for a closed catch-up is accepted without effect.
- `GET /pending`: `{deliveryIds:[uuid]}`; pending jobs only. **Paced:** at most one ID, and none while any delivery began less than 15 seconds ago (`SEND_GAP`), so replies leave the owner's number about four a minute, live or catch-up. A pending job queued under an earlier rules revision is marked held here (as `begin` would) so it cannot delay the jobs behind it.
- `POST /deliveries/{id}/begin`, body `{}`: locks the exact pending delivery, rechecks the current rule and suppression, then returns either `{send:false,state}` or `{send:true,deliveryId,recipientId,message}`. The row changes to calling before any provider action. A replay cannot authorise another call.
- `POST /deliveries/{id}/settle`: `{state:"sent"|"outcome_unknown",providerMessageId}`. Exact result replay succeeds; changed results conflict. “Sent” means WhatsApp accepted it, not a delivered/read receipt.
- `POST /opt-outs`: `{eventId,senderPhone,action:"STOP"|"START",observedAt}`. Event replay rules also apply. Older START cannot release a newer STOP. These controls are distinct from official Meta consent.

Rules, catch-ups, event admission and begin share a short Postgres lock. The unique `(rule_id,sender_sha256)` prevents repeated DMs across restarts and concurrent event callbacks. Editing a rule never re-sends an old reply; pending jobs from an earlier revision are held. Calling and unknown operations are never retried. Before a provider call, the adapter writes a calling marker. After a crash it settles that operation as unknown; after a lost settlement response it retries only the recorded settlement, never the DM.

## Catch-up: answering people who typed the keyword earlier

A rule answers new messages. A catch-up is the owner's explicit, bounded request for one **enabled** rule to also answer people who typed its keyword in its groups during the last 1 to 168 hours (the editor offers 6, 24, 48, 72 hours and 7 days; default 48). It is requested on the keyword screen ("Catch up on earlier messages" under an enabled rule) or by the operator tool `whatsapp_keyword_catchup`, and is refused unless the rule is enabled, the owner confirms again that the group's members were told the keyword requests this private reply, and no other catch-up is open. Requests and cancels are audited (`whatsapp.keyword.catchup`, `whatsapp.keyword.catchup.cancel`). Catch-ups live in AppSetting `whatsapp_keywords.catchups` (the latest ten); there is no migration, and the enquiries, events and suppressions are the existing tables.

What happens: Group HQ records the window (`since` = request time minus the hours, `until` = request time), the rule's groups and the rules revision, and offers it in `GET /rules`. The listener, for each group, starts from the newest message it has seen there (the anchor) and asks the owner's phone for the 50 messages before it, then the 50 before those, until it passes `since`, the phone says nothing earlier remains, or the phone stops answering. Each message inside the window that matches the rule and was not sent by the owner goes through the same durable outbox as a live request, as `catchup-events`, with the sender's phone resolved exactly as live (an unresolved identity is counted and never messaged). The event ID is the WhatsApp message's own, so a message seen both live and in a catch-up is one event. The listener then reports the group. Replies are released by `GET /pending` one at a time, about 15 seconds apart.

Limits, by design:

- **300 queued replies per catch-up.** Further matches are counted as over the cap, not queued and not recorded, so a later catch-up can still answer them.
- **Two hours.** A catch-up the listener has not finished within two hours of the request expires. Replies it had already queued still go out; unread groups show as not read.
- **Any rule edit ends it.** Saving any rule changes the revision: the catch-up is closed as "rules changed" and its unsent replies are held, exactly as an edit already holds unsent live replies.
- **Cancel** stops admission and holds that catch-up's replies not yet sent. Held replies are never sent later, and (as with any held reply) that person is not answered again by that rule.
- **Once per person per rule, STOP respected, unknown outcomes never retried**: unchanged, shared code.
- **The phone decides how far back it serves.** The listener can only read what the owner's phone still holds and is willing to supply to a linked device, and only while that phone is online. A group shows "stopped before the start of the period" when the phone supplied nothing earlier, and "earlier messages were not available" when it supplied nothing at all.
- **An anchor is required.** The listener must have seen at least one message in the group (live, or the owner's own) since it was updated to this version. Until then the group is retried, and reported unavailable shortly before the catch-up expires. Messages newer than the newest one the listener has seen are not reached by a catch-up; they are the live rule's job.
- **Names.** The phone's history copy often lacks the sender's display name, so `{name}` may become "there" for a catch-up reply unless the listener saw that person post while it was running.

How the listener reads history with the pinned Baileys 7.0.0-rc14 (`socket-client.cjs`, `catchup.cjs`): `socket.fetchMessageHistory(count, oldestMsgKey, oldestMsgTimestamp)` sends the owner's phone a peer request (`HISTORY_SYNC_ON_DEMAND`) carrying only the chat ID, the anchor's message ID and `fromMe`, its time in milliseconds and the count (50 a request is Baileys' documented maximum, for groups too). The phone answers, when it does, with a history-sync notice of type `ON_DEMAND` addressed to the account itself. Baileys would surface that as `messaging-history.set`, but only where `shouldSyncHistoryMessage` allows it, and its event buffer drops every message it has already emitted in a history set on that connection, so a second catch-up over the same days would silently read nothing. The listener therefore leaves that switch exactly as the personal-inbox setting decides it, and reads the notice itself from `messages.upsert` (the account's own notices only, only while a catch-up page is awaited) with Baileys' own `downloadAndProcessHistorySyncNotification`. A page is tied to its group by the messages' chat ID, never to the live path: earlier messages cannot enter `/events`.

`GHQ_WA_PAIR_ONLY=true` refuses all of it: no anchor is kept, the phone is never asked and nothing is submitted. Offline tests cannot prove what a real phone returns; run the live acceptance check in `tools/whatsapp-keywords/README.md` once before relying on it.

## Relaunch72 integration handoff

The keyword screen is the single owner editor. RL72 may add a brand-scoped entry that opens this existing editor, rather than another rule database. This patch has **no canonical CRM write/export API**. The recent enquiries are a separate intake/outbox, explicitly labelled as awaiting identity matching. They are not inserted into `CampaignLead`, and are not represented as signed Meta receipts or verified contact points.

A subsequent RL72 adapter must preserve source `whatsapp_web_group_keyword`, listener ID, event ID, rule ID/revision, brand and existing request digest. Match an existing verified canonical contact only when unambiguous; unknown/ambiguous identities go to review. A keyword request is permission for that promised reply, not general marketing consent. A dedicated read-scoped bridge contract and genuine owner permissions must be agreed before exporting these enquiries; do not reuse the sending adapter key for a member-facing UI or expose it in browser JavaScript.

1. Exact-source checks for the compatibility bridge and full candidate pass before production changes.
2. Publish/deploy the compatible bridge first. Its only functional addition is additive migration0010; existing journeys remain on the old implementation and no messages start.
3. Deploy the full candidate, verify `/healthz`, owner editor/auth and the adapter authentication rejection. Save no enabled rules as part of deployment.
4. With the founder's dedicated-access approval, save the adapter secret privately in Group HQ and the local adapter. The owner scans the QR, chooses a test group, and writes/explicitly enables one owned test rule. Run a real keyword/DM/replay/STOP acceptance check; do not infer that offline tests prove WhatsApp delivery.
5. For recovery, pause the listener first and restore the retained compatibility bridge artifact. It understands migration0010, leaves records intact and keeps the existing CRM working. Do not downgrade/drop tables containing event history. Official MHP/PP services are unchanged by this release.
