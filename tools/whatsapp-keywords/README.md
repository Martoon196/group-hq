# Portable Growth HQ group listener

See [the contract and release notes](../../docs/whatsapp-keywords.md).

1. In this directory, run `npm ci --ignore-scripts`. The pinned Baileys socket transport needs no Chrome window or browser profile.
2. Privately set `WHATSAPP_KEYWORD_ADAPTER_SECRET` to the dedicated value also saved on Group HQ, and `GHQ_WA_LISTENER_NUMBER` to the chosen account's international digits (no plus sign). Never use a Meta access token here. Set `GHQ_WA_DATA_DIR` to a private persistent directory if needed.
3. Run `npm start`. Open the private loopback address saved in `pairing-url.txt` beside your data directory **inside Codex**, then scan it with the selected WhatsApp account → Settings → Linked devices → Link a device. QR values stay in memory, never in terminal logs. The address survives process restarts; a stale QR expires automatically. For a pairing-only check, set `GHQ_WA_PAIR_ONLY=true`: group/contact reads, incoming-message export and sending are refused even after successful linking. Stop that process and restart without this flag to sync groups and run enabled replies.
4. Open `https://group-hq.onrender.com/crm/channels/whatsapp/keywords`. Choose the business and groups, write the keywords/reply, confirm the invitation requests that reply, and deliberately enable the rule.

Keep the process running. Ctrl+C stops it. Credentials and Signal keys use one encrypted atomic snapshot in your private data directory; keep its separate storage key private too. Session/outbox files are ignored by Git; don't share them. Messages require a matching group request, selected group and enabled rule: a new one as it arrives, or an earlier one only when you ask for a catch-up (below). Saving configuration alone sends nothing. Replies leave about one every 15 seconds, however many are waiting. This adapter has no Meta token and cannot replace the official MHP sender.

For personal one-to-one text, open Growth HQ's Inbox > Personal connections with this same listener running. Select **Collect personal WhatsApp conversations and available history** and save. Enable **Allow replies from this WhatsApp number** separately to reply in the original chat. The device collects incoming and outgoing text while online. With collection enabled, the next normal listener start advertises desktop history support and accepts history the phone supplies. An already-paired phone may supply fewer initial chats. It also requests older pages for known direct chats until the phone reports its earliest available message. The phone controls how much it supplies. Media history retains captions or media-type labels. The owner can link a conversation to an individual business CRM from the inbox.

## Catch up on earlier messages

A rule answers new messages only. To answer people who already typed the keyword, open the keyword screen, find the enabled rule and use **Catch up on earlier messages**: choose how far back (6 hours to 7 days), tick the confirmation and submit. With this listener running, it asks your phone for each of the rule's groups' earlier messages, a page of 50 at a time, and submits only those that match the rule inside the period. Group HQ then queues one private reply per person (never someone already answered by that rule, never someone who sent STOP, at most 300 per catch-up) and this listener sends them about one every 15 seconds. The screen shows progress and has a Cancel button.

What it needs: your phone online; this listener running and finishing within two hours of the request; and, for each group, at least one message seen by this listener since it was updated (it pages back from the newest message it has seen, so a group that has been silent since the update is retried and then reported as unavailable). It reads only as far back as the phone will supply. To be able to ask, the listener keeps one sealed file, `catchup/` in the data directory, with the newest message of each of your groups (message ID, time, sender ID and display name, and that message's text). Nothing else from a group is kept, and nothing is read back or submitted unless Group HQ has an open catch-up. `GHQ_WA_PAIR_ONLY=true` switches all of this off.

**Updating the one existing listener for catch-up.** Stop the running process (Ctrl+C), then in this directory: `git pull`, `npm ci --ignore-scripts`, and `npm start` with the same environment and the same `GHQ_WA_DATA_DIR`. Do not delete or move the data directory and do not scan a new QR: the sealed session, the outbox and the settlement files are reused as they are. Deploy Group HQ first or second; either order is safe (an older listener ignores catch-ups, and this listener asks for nothing until the server offers one).

**Live acceptance check, once.** Offline tests cannot prove what a real phone returns. In a test group you control, with a second phone: (1) with the updated listener running, post any message in the test group so the listener has an anchor; (2) from the second phone type a test keyword in the group that no rule covers yet (twice, a few minutes apart); (3) create and enable a test rule for that keyword in that group only and confirm no reply arrives yet; (4) request a 1-hour catch-up for it; (5) confirm the second phone receives exactly one private reply within a minute or two, the screen shows the group as read with 2 matching messages and 1 reply queued and sent, and the terminal shows no message text, name or number; (6) request the same catch-up again and confirm no second reply arrives; (7) pause the test rule. If the group stays "waiting for the listener" or ends "not available", the phone did not answer the history request: keep the phone unlocked and online and try again before using catch-up on a real group.

Update the one existing listener process in place. Reuse its private data directory and sealed socket session. The personal controls start off. To pause, clear them in Personal connections. On server rollback the older server ignores the separate personal setting, and its group rules continue to work. The scoped worker retries recorded send outcomes without sending again after recovery.

If a catch-up reads less than expected, start the listener once with `GHQ_WA_CATCHUP_TRACE=true`. It then logs the shape of each request to the phone and each answer (counts, flags and times only: never a message, a name, a number or an ID), which shows what the phone returned. When a group's very first answer comes back empty, the listener asks once more with the stored message's time in seconds before it accepts that nothing earlier exists.

Run offline matcher/auth/catch-up checks with `npm test`. These checks do not connect WhatsApp or prove delivery, and they cannot prove that a real phone answers a history request.
